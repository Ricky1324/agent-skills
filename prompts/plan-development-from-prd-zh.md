# 根据 PRD 与架构拆解开发任务

请以技术负责人的视角，根据产品需求文档（PRD）、系统架构和现有项目状态，制定可交给开发者或 AI 编程助手执行的开发计划。任务应范围清晰、依赖明确、可验证，不以任务数量或固定阶段代替实际规划。

本次只输出计划，不修改代码或文档，不创建外部工单，不部署。

## 输入信息

- 项目名称与简介：【填写】
- PRD：【提供正文或文件路径】
- 系统架构设计：【提供正文或文件路径；未确定时注明】
- 现有仓库路径与项目状态：【填写；新项目注明尚未初始化】
- MVP 与非目标：【填写；不明确时注明待确认】
- 开发模式、成员职责与可投入时间：【例如：个人开发，每周 15 小时】
- 目标周期或截止时间：【填写；未确定时注明】
- 已确定的技术栈、部署环境和外部依赖：【填写；未确定部分注明待确认】

## 规划前的检查

1. 阅读所提供的 PRD 和架构；已有仓库时，检查适用的 `AGENTS.md`、`README`、相关设计文档、代码和测试，确认当前状态。不要把已实现能力重复列为待开发任务。
2. 概括目标用户、核心流程、MVP、非目标和职责范围，区分已完成、待开发、待确认内容，注明重要判断的来源。
3. 检查需求、架构与实现之间的缺失或冲突。不要自行添加产品功能、技术选型或接口约束，也不要把示例当成确定要求。
4. 关键输入不足、会改变范围或技术路线时，先提出少量必要问题，暂停依赖该答案的规划；可先分析不受影响的部分。次要未知项列为“待确认”，相关计划注明条件，不伪装成已确定安排。

## 任务拆分原则

- 优先按可验证的用户流程或系统能力组织任务，尽早贯通最小核心流程。初始化、数据库、后端、AI、前端、联调、测试和部署只是参考，不要求每个项目都包含这些阶段。
- 根据实际依赖安排顺序；测试与集成验证应随任务推进，不全部留到最后。高风险技术、外部服务和模型效果不确定时，先安排小范围验证任务，并注明成功标准及失败后的决策点。
- 每个任务尽量只解决一个问题；前置依赖满足后，应能单独执行和验收。跨模块任务明确接口和边界，不把共享文件或环境的改动无条件安排为并行工作。
- 以 1～3 小时作为拆分目标，不强行压缩复杂工作。超出时说明原因并尽可能拆分；未知项先验证再估算。工作量是估算，注明范围、依据和不确定性，避免虚假精确。
- 区分开发工作量与日历时间，考虑个人可投入时间、成员职责、外部等待、联调和审查。周期不足时，指出取舍，不自行扩大 MVP 或承诺不现实的交付日期。
- 验收标准应体现可检查的行为、输出或测试结果，包含适用的异常路径，不能只写“功能正常”。测试方式应与风险相称，不为形式完整添加无意义测试。
- 仅安排需求与架构支持的功能和工具，不默认需要 JWT、RAG、Docker、CI/CD 或特定部署平台。适用的权限、隐私与数据处理要求应纳入相关任务；要求缺失时标为待确认。

## 输出方式

### 第一部分：范围与现状

概括已确认范围、当前已完成能力、待开发能力、非目标、关键约束，以及缺失或冲突的输入。说明本次计划的依据和限制。

### 第二部分：任务清单

按依赖顺序输出任务。每个任务使用以下格式：

- **Task ID / 名称**：使用稳定且唯一的 ID。
- **目标与需求依据**：说明对应的 PRD 条目、架构部分或验证问题。
- **开发内容与边界**：说明本任务做什么及与其他任务的分界。
- **输入与输出**：所需资料、接口或数据，以及可交付结果。
- **依赖任务**：引用实际 Task ID；无依赖时注明。涉及外部条件时单独列出。
- **预计工作量**：估算范围、主要依据和不确定性。
- **优先级**：说明是否阻塞核心流程，以及是否属于 MVP。
- **验收标准与验证方式**：给出可检查结果；命令仅引用项目实际支持的命令，尚未建立时说明拟采用的验证方式。
- **涉及文件或交付物**：已有文件使用真实路径；新文件标为“建议路径”，结构未定时描述交付物，不编造确定路径。
- **AI 执行方式**：说明适合一次完成、分步实现、辅助分析或需要先由人作出决策，并给出原因。分步时说明各步骤的目标和检查点。
- **审查与测试建议**：说明需要人工审查的内容、是否适合先写测试，以及完成后必须如何验证。不要把 AI 生成代码等同于验收完成。
- **开发建议与风险**：仅列影响执行的关键事项。

对仅验证可行性的任务，明确区分验证产物与可交付实现，不默认把试验代码用于生产。

### 第三部分：依赖与开发路线图

列出关键依赖链、可并行任务及其限制。依据目标周期和可投入时间，使用周时间轴或 Mermaid 甘特图安排任务，并注明估算前提和主要缓冲。

没有足够时间信息时，先输出相对顺序与工作量，注明无法确认周计划，不虚构日期。

### 第四部分：关键里程碑

按可用能力定义里程碑，例如“用户可完成一次核心流程”，而非仅写“数据库完成”。每个里程碑注明包含的 Task ID、可演示结果和验收条件。

### 第五部分：风险与执行建议

指出最可能延期的任务、关键技术难点、外部依赖、必须人工决策或审查的内容，以及周期不足时建议缩减的范围。

汇总 AI 执行的共同约定：每次提供任务范围、必要上下文、接口和验收条件；完成后检查差异并执行相应验证；发现输入冲突或范围变化时先报告。每项任务的执行策略已列入任务清单，此处不重复逐项输出，也不承诺任何模块可免于审查和验证。
