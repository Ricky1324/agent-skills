# 按职责范围审查新增项目资料

请对项目中新加入的资料做一次按职责范围进行的审查（scope-aware audit），判断它们是否影响我当前负责的工作。

## 本次审查范围

- 项目路径：【填写项目路径】
- 新增资料路径：【填写需要审查的文件或文件夹，可列多个】
- 我负责的模块和职责：【填写已知职责；不明确时注明待确认】
- 重点参考文档：【填写设计文档、职责划分或接口文档路径；没有时注明无】

先给我分析结果，不要修改代码或文档，也不要开始实现新功能。

## 审查步骤与边界

1. 先查看新增资料的文件名、目录结构、文件类型、大小和可获得的元数据，说明各文件夹分别包含什么。
2. 阅读现有 `AGENTS.md`、`README`、重点参考文档及相关 `docs`，再按需要检查当前代码和已有职责划分。只读取实际存在且与判断有关的内容，不预设项目具有某种架构或模块。
3. 对照现有设计和实现，判断哪些新增内容与我的模块直接相关，哪些仅用于理解客户业务，哪些属于演示参考或其他成员职责。
4. 如果资料包含新的数据源、字段、输入/输出格式、接口约束、业务规则、评估要求或系统流程，请明确指出，并区分已确认的新要求、样例或演示行为、与现有资料的冲突以及待确认事项。不要直接把样例或演示行为当成正式需求。
5. 不要因为仓库中出现 Web Demo，就默认我要负责网页开发。若职责范围无法确认，请列出已知证据和待确认问题，不要仅凭文件所在目录、技术栈或演示内容推定归属。
6. 对视频、大型数据文件或其他处理成本较高的资料，不要一开始完整处理。优先使用元数据、说明文档和适量样例；记录抽样或未读取部分造成的分析限制。只有确实存在无法通过其他资料回答的相关问题时，才建议进一步分析，并说明目标文件、需要验证的问题和建议范围。
7. 对 Web Demo，只提取有助于判断我的模块需求的信息，例如输入/输出格式、用户流程、API contract、数据字段、业务规则、系统交互，以及前端对后端或 AI 能力的依赖。不需要分析或实现与我职责无关的 UI、CSS、页面布局等内容。
8. 每项重要判断都应注明依据的文件路径，适用时补充章节或代码位置。区分资料中的事实与自己的推断；无法确认的事项标记为“未确认”，不要自行假设。资料相互冲突时说明冲突，不要自行选定新的要求。

## 输出方式

### 第一部分：新增资料概览

按文件夹或资料组概括内容、用途和本次读取范围。列出影响结论的未读取、无法读取或仅抽样检查的资料，避免把局部检查说成完整审查。

### 第二部分：与职责范围的关系

将资料分为以下几类；职责归属不明确的资料单独列为“未确认”：

- **与我的模块直接相关**：说明为什么相关、影响哪个模块，以及我需要进一步阅读或处理哪些文件。
- **有助于理解业务**：说明提供了什么背景，以及为什么目前不需要修改实现。
- **属于 Web/UI/前端或其他成员职责**：说明职责判断的依据，以及我目前是否只需关注其中的接口或模块依赖。

同一资料包含多种用途时，按相关内容分别说明，不必强行把整个文件归入单一类别。

### 第三部分：对现有项目的影响与待确认项

仅分析适用的维度：

- 数据源与 data schema
- retrieval / RAG
- evaluation
- backend / API
- system architecture 与系统流程
- assumptions / constraints
- documentation

对每个适用维度，说明新增资料是否影响我负责的模块、与现有依据有什么差异，以及是否需要确认。明确区分“有变化”“在已检查范围内未发现变化”和“未确认”；若发现文档缺口，仅提出建议，不修改文档。

### 第四部分：当前最值得做的下一步

按优先级只列与我当前职责直接相关、最值得做的少量行动，包括应进一步阅读的文件和需要确认的问题。不要扩张职责范围，也不要把全部资料都列为必读。如果目前没有证据支持实现变更，明确说明。
